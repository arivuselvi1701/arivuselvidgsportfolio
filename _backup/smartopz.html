SmartOpz

From a disorganized app to an organized, flexible platform.

I led the redesign of SmartOpz — an all-in-one HRMS — turning a rigid, hard-to-use internal tool into a configurable system any company can shape to fit how it actually works.

01 Business Context

SmartOpz is an all-in-one HRMS — covering People, Requests, Time, Projects, Procurement, Assets, Money, Partners, and Documents. It was built for a client who needed one system to run HR, finance, and operations, without forcing their company into someone else's fixed process.

This is a complete revamp of an app the client already had, not a build from zero.

02 The Challenge

Nothing about the existing app felt organized. There was no coherent flow, the struggle for people using it day to day was real, and the tool assumed every company runs HR the same way — when in practice, none of them do.

01

Organize

Turn a disorganized app with no real flow into something people can actually use day to day.

02

Flex

Let any company shape approvals, roles, and rules to fit how it actually works — not one fixed process.

03

Adopt

Make sure a first-time user can get value immediately, without configuring anything first.

The client's own diagnosis was clear: the fix wasn't just tidying up screens, it was adding real flexibility — organized enough to use, configurable enough to fit anyone.

03 My Approach

Four moves turned a disorganized tool into a governed, configurable system.

01

Learn the real domain

Studied the existing app, talked to the client, and benchmarked competitors (Keka, Zoho People, Horilla, Rippling) — more on the domain research in Team Alignment.

02

Design the core pattern

Built one repeating logic — request, then approval, then outcome — so a user who learns it once understands most of the product.

03

Build the configuration layer

A Configuration Hub lets each company set its own roles, ticket types, approval chains, and rules, reshaping the product to fit them.

04

Ship defaults, not a blank slate

Key ticket types shipped with working defaults, so a new user could use core features immediately — configuration stayed available, not required.

On top of the design work, I acted as project owner — coordinating across teams and keeping deliverables on time — and owned QA and client presentation after development.

04 Key Decisions

The system worked because the trade-offs were deliberate.

# Decision Why
01 One repeating pattern Request → approval → outcome runs through every module. Learn it once, and most of the product reads itself.
UX principle — Jakob's Law: People expect new tools to work like tools they already know. One repeating pattern across all nine modules means less to learn and less to remember.
02 A single Configuration Hub Roles, ticket types, approval chains, and rules live in one place that reshapes the whole product — not scattered toggles.
UX principle — Flexibility & Efficiency of Use: A good system works for both new and advanced users. The Configuration Hub is the advanced-user side of that balance.
03 Guided wizards over dense forms Complex, multi-part tasks (leave, payroll, ticketing) are broken into short steps instead of one long form.
UX principle — Hick's Law & Progressive Disclosure: More choices at once means slower decisions. Splitting a task into small steps, and showing options only when needed, keeps each screen light.
04 Defaults for the common case Leave Request defaults to Reporting Manager and HR as approvers — works out of the box for most companies, still editable.
UX principle — Pareto Principle (80/20): Instead of asking every company to set up from zero, we built the default for the common case, and left room to edit for the rest.
05 CAPEX/OPEX classified by the right role Moved from the person raising the request to finance/inventory staff at the bill stage, who actually know the answer.
UX principle — Error Prevention: A form is only as good as the person filling it in. Moving a decision to the person who actually knows the answer prevents bad data before it happens.

06 The System

An employee doesn't take leave, they raise a Leave Request. No one buys a laptop, someone raises a Procurement Request. Once it's approved, the system turns it into the real outcome — leave gets deducted, a bill gets raised, an asset gets handed over.

This one pattern repeats across all nine modules, so learning it once helps a new user understand most of the product. The Configuration Hub sits underneath, reshaping how every module behaves per company.

07 Content Model

At first, everything was fully configurable, with nothing set by default. Some flows didn't work at all until someone configured them — without a Leave Request ticket set up, the leave flow wouldn't run, which affected leave balances and timesheets too. Asset Request and Procurement Request had the same problem.

To fix this, key ticket types shipped with defaults, kept fully editable. A similar issue in Procurement — classifying a purchase as CAPEX or OPEX — was moved from the person raising the request to finance or inventory staff at the point the bill is raised, since they're the ones who actually know the difference.

We didn't get these right the first time. We noticed the problem in use, and fixed it from there.

09 Team Alignment

Ticketing, CAPEX, and OPEX were new to me and the team, and the client's requirements weren't fully clear at the start. I went and learned it directly — talking to people who work with ticketing systems every day, and running sessions with a CA to understand how CAPEX and OPEX really work.

Not every client request is the right call, but not every one is wrong either. If a request had a real reason behind it, I built it. If it didn't, I explained the risk clearly and let the client decide.

The tools we used were core to how this was built. The hard part wasn't using them — it was explaining my thinking clearly enough that the output matched what I actually wanted, and staying sharp about checking and re-prompting instead of settling for whatever came out first.

10 Results

SmartOpz is live and used daily inside the client's own company (not yet by their customers). The core workflows and unified system have generally worked well for people; some users still find configuration confusing, which we're actively working on.

Before → After
Every ticket type fully configurable, nothing worked by default → Key ticket types ship with working defaults, fully editable
CAPEX/OPEX classified by whoever raised the request → Classified by finance/inventory staff who know the answer
No consistent pattern across modules → One request → approval → outcome pattern everywhere
Fixed process, same for every company → Configuration Hub adapts the system per company

We keep iterating based on this feedback. It's an ongoing process, not a finished product.

Note: SmartOpz doesn't yet have a usage-analytics dashboard, so results here are qualitative — drawn from direct client feedback rather than measured funnel or adoption numbers.

11 What I Learned

01

Design for many companies, not one client

Every flow was checked against one question: would this work for a company that isn't ours?

02

Sketch before you commit

For ticketing and CAPEX/OPEX, I sketched a few options and weighed trade-offs before picking one — rather than committing early and fixing it later. Even so, we missed some edge cases and had to work around technical limits.

12 Next Step

We strive to give our best. I visit the app regularly and test flows at random, which often brings a new edge case to light. I'm also fortunate to have a client call every week, and together we keep finding ways to make the product better, every day. Whenever a new idea comes up, I reason through it carefully before we build it, so each change makes the product a little better than before. It's a continuous process, and one we genuinely enjoy being part of.
